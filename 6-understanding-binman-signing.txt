################################################################################
UNDERSTANDING BINMAN SIGNING
Deep Dive into TI K3 / AM62x Secure Boot Flow
################################################################################

================================================================================
1. INTRODUCTION TO BINMAN ARCHITECTURE
================================================================================

Binman is the primary packaging tool used in U-Boot to assemble multiple
binaries (SPL, U-Boot, ATF, OP-TEE, Firmwares) into a single flashable image
(e.g., tiboot3.bin, tispl.bin). For TI K3 devices like the AM62x, binman also
manages the cryptographic signing required by the ROM and System Firmware.

The signing flow follows a hierarchical chain:
DTS (Config) -> Entry Type (Logic) -> Bintool (Execution) -> OpenSSL (Tool)

================================================================================
2. KEY SOURCE FILES AND DIRECTORY MAP
================================================================================

2.1 Configuration (The "What")
-------------------------------
These files define which binaries are packaged and which keys are used.
- Location: u-boot/ti-u-boot/arch/arm/dts/k3-am625-sk-binman.dtsi
- Key Property: 'keyfile = "custMpk.pem";' inside signing nodes.

2.2 Entry Types (The "How")
----------------------------
These Python scripts define the logic for TI-specific certificates.
- Location: u-boot/ti-u-boot/tools/binman/etype/
- ti_secure.py: Logic for general blobs (ATF, OP-TEE, SPL).
- ti_secure_rom.py: Logic for ROM bootloader images (tiboot3.bin).
- x509_cert.py: Base class for X.509 certificate generation.

2.3 Bintools (The "Execution")
-------------------------------
The wrapper that calls the actual system 'openssl' binary.
- Location: u-boot/ti-u-boot/tools/binman/btool/openssl.py
- Key Function: 'run_cmd' builds the command line for openssl.

================================================================================
3. THE SIGNING WORKFLOW STEP-BY-STEP
================================================================================

1. DTS Parsing:
   Binman reads the .dtsi and identifies a signing node (e.g., ti-secure-rom).
   It extracts the 'keyfile' property (currently a filename).

2. Data Collection:
   Binman gathers the binaries listed in the 'content' property (e.g.,
   u-boot-spl.bin).

3. Config Generation:
   The entry type (ti_secure.py) generates a temporary OpenSSL configuration
   file. This file contains TI-specific OIDs that the TI ROM/TIFS expect,
   such as software revision and image integrity hashes.

4. Bintool Call:
   The entry type calls the openssl bintool method (e.g., x509_cert_sysfw).

5. OpenSSL Execution:
   The openssl.py bintool executes the system command:
   $ openssl req -new -x509 -key [keyfile] -nodes -outform DER -config [cfg]

6. Assembly:
   Binman prepends the resulting certificate to the binary data to create the
   final signed image.

================================================================================
4. SOFTHSM INTEGRATION STRATEGY
================================================================================

Because binman uses a central bintool (openssl.py) for all signing operations,
enabling HSM support is a surgical change to that single file.

By modifying openssl.py to detect a 'pkcs11:' prefix in the 'keyfile' string,
we can force openssl to use the engine:

Patched Command Logic:
$ openssl req -engine pkcs11 -keyform engine -key "pkcs11:..." [rest of args]

================================================================================
6. CORE DEFINITIONS AND CLARIFICATIONS
================================================================================

6.1 Entry Type (The "Plugin" or "Template")
--------------------------------------------
In Binman, an Entry Type is a Python class (located in `etype/`) that defines 
how a specific piece of data should be processed and packaged. 
- While standard entry types might just place a binary at an offset, TI-specific 
  entry types (like `ti_secure.py`) act as advanced templates.
- They contain the logic to calculate hashes, generate OpenSSL configurations, 
  and trigger the signing process before the final image assembly.

6.2 OID (Object Identifier)
----------------------------
An OID is a standardized, globally unique numerical string used to identify 
specific data fields within a digital certificate (e.g., `1.3.6.1.4.1.294.1.3`).
- TI uses custom OIDs to embed non-standard security metadata that the TI Boot 
  ROM/TIFS requires.
- Embedded Data Includes: Image integrity hashes, software revision numbers 
  (to prevent rollback attacks), and Security Core IDs.
- These OIDs allow the TI hardware to locate and verify security parameters 
  during the power-on boot sequence.

6.3 Bintool Call (Manager-to-Worker Delegation)
------------------------------------------------
This represents the delegation of execution from the Entry Type (the "Manager") 
to the Bintool (the "Worker").
- The Entry Type knows *what* security data is required but does not interact 
  directly with the system shell.
- Instead, it "calls" a method in the `openssl.py` bintool, passing it the 
  necessary file paths and TI-specific parameters.
- The Bintool is the wrapper responsible for constructing the final command 
  string and executing the `openssl` binary on the host system.
- This architectural split allows for centralized HSM integration; by patching 
  the `openssl.py` bintool, we enable HSM support for all entry types that 
  utilize it.

6.4 The OpenSSL System Tool
----------------------------
The "OpenSSL (System Tool)" is a standard cryptographic utility installed on 
the host Linux system (typically `/usr/bin/openssl`).
- It is NOT part of the U-Boot source tree.
- Binman relies on the host's version of OpenSSL to perform all RSA/ECC 
  signing operations.
- By configuring the host's OpenSSL to use the `pkcs11` engine, we can 
  transparently redirect signing requests from Binman to SoftHSM.

7. FUNCTIONAL CALL STACK MAPS
================================================================================

7.1 tiboot3.bin (ROM-Signed HS Image)
--------------------------------------
This image is the first to boot and is verified by the hardware Boot ROM.

+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| Step | Component / File          | Functional Call & Parameters                | Output / Intermediate        | Notes                                                |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 1    | k3-am625-sk-binman.dtsi   | Binman Parser (Reads ti-secure-rom node)    | self._node (DTS Object)      | PHASE: CONFIG. Identifies keyfile and targets.       |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 2    | ti_secure_rom.py          | ObtainContents() -> GetCertificate('rom')   | True / False                 | PHASE: LOGIC. Starts TI-specific ROM signing.        |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 3    | x509_cert.py              | GetContents(required=True)                  | input_data (Raw SPL Bytes)   | PHASE: DATA. Pulls u-boot-spl.bin into memory.       |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 4    | u-boot-spl.bin            | tools.write_file('input.tiboot3...', data)  | input.tiboot3... (Disk File) | STAGING: Temporary copy of SPL for OpenSSL.          |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 5    | openssl.py                | x509_cert_rom(input, config, ...)           | config.tiboot3... (Disk File)| TI OID GEN: Calculates SHA512 and writes config.     |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 6    | openssl.py                | self.run_cmd('req', '-new', ..., key_fname) | Shell Command String         | EXECUTION PREP: This is our SoftHSM injection point. |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 7    | openssl (System Tool)     | openssl req ... -config config.tiboot3...   | cert.tiboot3... (Disk File)  | CRYPTO: Actual OpenSSL runs and creates certificate. |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 8    | ti_secure_rom.py          | SetContents(cert_data)                      | self.data (Updated Entry)    | INTEGRATION: Certificate assigned to entry.          |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
| 9    | Binman Core               | [cert.tiboot3...] + [u-boot-spl.bin]        | tiboot3.bin (Final Binary)   | ASSEMBLY: Glues cert to SPL front.                   |
+------+---------------------------+---------------------------------------------+------------------------------+------------------------------------------------------+
